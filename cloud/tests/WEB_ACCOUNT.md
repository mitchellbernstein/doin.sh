# Browser account E2E

This scenario covers the real `/account` browser UI against a local Miniflare fixture with synthetic email and Stripe responses. It exercises browser authentication, independent personal and team billing, plan/seat confirmation, team legal acceptance, payment recovery, and a checkout return. It must never use the production origin, a real mailbox, live Stripe credentials, or a real purchase.

## Failure census

- Login approval is granted by opening an email GET, a stale/canceled flow, an incorrect PKCE challenge, or a code entered in the wrong browser.
- Session tokens or email link tokens appear in the URL, referrer, page source, browser-visible diagnostics, screenshot, or committed artifact; untrusted account/team text is interpreted as HTML.
- The account screen hides BYO AI behind doinMORE copy, or a MORE plan change switches plans or charges before a server quote is explicitly confirmed.
- Confirmation amount, quote ID, interval, or expiration is missing, stale, changed between preview and submit, or accepted after the customer cancels renewal. After Stripe update, incomplete subscription data can make server reconciliation fail as “billing busy”; the fixture must return the full customer, status, item ID, price, quantity, and period-end fields. A pending plan payment is displayed as the existing interval plus a pending target, never as an applied switch.
- Payment recovery, payment-method update, team purchase, seat change, cancellation, resume, or personal renewal cancellation occurs from a page load, polling, or an unconfirmed click.
- A payment-method, invoice, or checkout URL can escape the expected HTTPS Stripe host; malformed URLs or provider errors leave a loading state or expose provider details.
- Team owner and member controls are confused; a member sees an owner action or triggers repeated owner-only 403 requests. Team data or subscription state is mixed with personal MORE state.
- Team creation skips visible commercial terms, version acceptance, or legal-entity entry; accepting terms silently starts checkout; checkout silently mutates paid seats.
- Authenticated team terms are fetched without the bearer token, causing `/v1/teams/terms` to return 401 and hiding commercial-team creation behind a generic busy message.
- Seat upgrades charge without showing the exact proration quote; reductions hide that they apply at renewal only; proposed seats can undercut occupied members.
- A `status=success` URL grants team entitlement, suppresses server refresh, or shows an active plan when authenticated server billing says inactive. `status=canceled` is only explanatory UI text.
- A checkout-return banner appears while the account remains on the MORE tab, hiding the team state that the URL describes; the return should open Teams after the first authenticated refresh without forcing later user navigation.
- Owner's personal subscription is canceled without a separate confirmation, despite an active team subscription. UI implies data/subscription transfer or duplicate billing is reconciled automatically.
- The owner’s personal renewal confirmation relies on a browser `prompt()` that the in-app browser cannot display; the intended phrase is unreachable and the action cannot be safely completed.
- Receipt export omits the expected content, fails to download, or includes browser credentials.
- Browser requests keep polling billing/payment state or repeat mutations without user action; one click creates duplicate requests.

## Run

Use a clean browser profile and an unused loopback port. Start `node tests/web-browser-fixture.mjs` with `DOIN_FIXTURE_PORT` and a unique `DOIN_FIXTURE_MAIL_FILE` path. Record the fixture PID and exact command. Use the synthetic `fixture@example.com` account only. The fixture prints its origin, PID, and temporary mail-file path, never session tokens, email URLs, or confirmation codes. Read the captured synthetic email URL only as temporary input and open it in the second browser tab. The email file is secret test input; delete it after the fixture stops and do not copy it into the evidence artifact. Stop the exact fixture PID after all cases and verify it exited.

Fixture controls are served only by the local Miniflare wrapper under `/__fixture/`; do not expose these routes in a deployed Worker. `GET /__fixture/state` reports synthetic checkout/subscription status and pending count. `POST /__fixture/complete-checkout` with `{}` explicitly settles the latest unexpired open checkout and is the only action that grants fixture billing entitlement. `POST /__fixture/hold-payments` with `{ "hold": true|false }` toggles pending subscription updates; `POST /__fixture/settle-payment` with `{}` explicitly applies them. `POST /__fixture/personal-status` sets the seeded personal status to `active`, `past_due`, `incomplete`, `unpaid`, or `canceled`. `POST /__fixture/provider` with `{ "down": true|false }` simulates provider outage. `POST /__fixture/redirects` with `{ "invalid": true|false }` makes generated redirect URLs use an untrusted host. `POST /__fixture/preview-amount` with `{ "amount_due": <0..10000000> }` changes the next synthetic proration quote. `POST /__fixture/role` with `{ "team_id": "...", "role": "owner"|"member" }` changes only the seeded account’s membership role. Each control rejects unknown fields and invalid values. None sends email, charges a card, or contacts Stripe.

## Scenarios

1. **Browser sign-in and security.** Start email sign-in in browser A. Open the synthetic message link in browser B; verify the confirmation page requests the six-digit code, and that GET alone does not approve. Enter the code from A only in B, then confirm A signs in. Start another flow, cancel A, approve its message in B, and verify A stays signed out. Reload A after successful sign-in and verify the session restores without bearer or PKCE material in the URL. Confirm email, team name, and legal entity containing `<img src=x onerror=alert(1)>` render as text.

2. **MORE plan lifecycle.** In the authenticated MORE section, verify BYO AI remains free and no text says AI or on-device tasks require doinMORE. Start with active monthly MORE. Choose annual, request a preview, inspect amount/currency, target interval, expiry and proration date, then confirm the displayed amount. Verify the subsequent Stripe subscription read includes matching customer, status, item ID, target price, quantity and current-period end; successful confirmation changes the interval only after that read. With payment hold enabled, verify one confirmation and a result that preserves monthly as applied while showing annual as pending. Settle through the fixture control and refresh to verify server truth. Repeat with a stale quote, changed amount, expired quote, provider error, and a canceled-renewal subscription; all must leave the current plan unchanged and show a recoverable message. Resume renewal explicitly before attempting another plan change.

3. **MORE recovery and payment method.** Set the fixture to a past-due subscription with an open invoice. Verify recovery appears only after a user click and validates the returned `invoice.stripe.com` URL. Verify payment-method management appears only for an eligible active subscription, is user initiated, and accepts only `billing.stripe.com`. Return to the account and refresh authenticated billing state.

4. **Team acceptance and first checkout.** Open Teams and verify both `/v1/teams` and `/v1/teams/terms` load with the authenticated session; terms must not fail with 401 or hide creation. Verify existing team choices load after login while MORE remains visible and unchanged. Create a hosted team by entering a team name and legal entity, reviewing the full commercial terms/version, and explicitly accepting. Verify creation does not open checkout or start billing. Select seats and review annual total plus the team identity before the explicit checkout click. Verify checkout points to HTTPS `checkout.stripe.com`; stop at the fixture boundary, with no payment.

5. **Secure checkout return and team billing.** Load `/team/payment?status=success` directly while authenticated. After the first authenticated refresh, show the Teams section alongside the return banner; a later refresh must preserve whichever section the user selected. The UI must fetch `/v1/teams` and authenticated team billing and show inactive until the provider response says active. Repeat with `status=canceled`, unknown status, and an unauthenticated browser. Query values must never affect entitlement. With a fixture-active team, verify owner-only paid/next-renewal seat counts, renewal date, payment recovery, payment method update, receipt download, cancel, and resume. Owner cancellation/resume each require a clear explicit confirmation. Receipt should download from a Blob with no bearer in the filename or contents.

6. **Team seat changes and coexistence.** Increase seats above paid capacity. Verify preview displays the exact immediate amount and seat count, then require a separate confirmation using that exact amount, quote/preview identifiers, and proration date. Retry with an altered amount and stale preview; paid capacity must not change. Reduce seats below next-renewal quantity but not below occupied seats; verify copy clearly says reduction starts at renewal and does not refund current term, and require a separate confirmation. Verify an occupied-seat reduction is refused. With an active team as owner and active MORE whose renewal is not canceled, show a separate “Cancel personal doinMORE renewal” action. Hide this action after renewal is canceled. Clicking it reveals an accessible exact-phrase input and separate confirm/cancel buttons; typing `cancel personal renewal` alone makes no request, and only clicking confirm sends it. Do not use a browser prompt. Do not claim data or subscription is transferred. Team billing remains independent.

7. **Member role, resilience, and logout.** Sign in as a non-owner member; list the team and show role, but hide owner billing controls without issuing owner billing requests. Exercise team list/provider outages, malformed redirect URLs, double-clicks, and sign-out. Errors stay generic, buttons recover, no purchase/cancel occurs, and the old session is rejected after logout.

## Evidence

Save a private `cloud/artifacts/web-account-browser.json` containing the fixture command, source revision, browser/version, synthetic scenario names, pass/fail results, screenshot paths, request-count/assertion notes, exact fixture PID, and `fixtureStopped: true`. Capture screenshots and accessibility snapshots for signed-out, active MORE, team-owner, team-member, pending confirmation, and checkout-return states. Redact email addresses, six-digit codes, email confirmation links, bearer tokens, PKCE verifiers, browser storage, customer/payment IDs, and full provider URLs. Store only host and pass/fail for redirect assertions. Screenshots must not show the code or any credential. Artifacts must be reproducible with the same fixture command and local source revision.
